# X-Post（Geeklog 2.2.2）

管理画面で公開中の記事を選択し、紹介文を編集・プレビューして、X公式APIへ1件投稿するプラグインです。1記事または日英2記事の紹介とURLを1投稿にまとめられます。定期投稿・予約投稿、画像アップロードはありません。記事取り込み（`happa-article-inbox`）が、記事パッケージの `announce_on_x: true` と投稿設定「記事取り込みからの告知を許可する」の両方が有効な時だけ、取り込み直後にこのプラグインの投稿処理で1回告知できます（下記「記事取り込みからの告知」）。画像付きの紹介は記事側のリンクカード表示に依存します。

### 未対応返信の受信箱

管理画面は未対応返信と未送信ドラフトを先頭に表示します。承認待ち、承認済み・未送信、送信失敗、送信中、結果不明を区別し、返信投稿記録で送信成功が確認できたものだけを非表示にします。承認記録だけでは送信済みと扱いません。既存の承認済みデータも自動的に再表示します。通常の完了履歴、見出しの連番、設定移動の案内は表示しません。履歴JSONは削除せず、重複防止に利用します。

画面ヘッダーはX-Postの投稿・返信確認・ローカル下書き承認の操作説明だけに絞ります。外部自動化の巡回頻度、X側承認待ちの理由、契約・請求上限設定、利用状況数値は表示しません。既存の告知間隔ガード（既定24時間）・8時間ガード・月額20ドルのローカル予算制限と返信無効の実装は変更しません。

改善項目へ登録又は関連付け済みのお礼ドラフトは「下書きを承認」1回で承認できます。CSRF・本文/投稿先の版・重複返信・改善項目の確認情報を再確認し、実行者と承認時刻を非公開feedback.jsonへ保存します。承認だけでは送信せず、承認済み・未送信として残します。Xの承認待ちによる返信無効を維持し、無効中は送信ボタンも無効です。将来別途送信ポリシーを有効化した場合だけ、承認内容を元の署名付き返信確認フローに引き継ぐボタンを出します。失敗は未送信として残し、送信中・結果不明には再送操作を出しません。返信取得データが失われても送信記録から失敗・結果不明を表示します。「見送る」も未送信として残します。質問・要確認は「確認済みにする」で一覧から外せますが、未分析コメントは分析待ち表示だけにします。

既存の本文保管期限30日は維持します。承認済みで未送信の項目は90日の通常整理後も確認用メタデータを残し、本文期限超過時は再作成が必要な旨を表示します。送信成功後は通常どおり整理できます。表示20件ごとにページを分け、画面表示だけで有料APIを再照会しません。

API設定はコンフィギュレーションだけに表示します。旧settings.phpの通常アクセスは303でconfiguration.php#xpostへ転送し、正規のグループ移動フォームからX-Postを選択します。埋め込み取得・保存・接続確認用の?embedded=1エンドポイントは維持します。

## 配置と初期設定

1. `Deploy-XPost.ps1 -GeeklogRoot Y:\geeklog\2_2_2` を実行します。変更するのは `plugins/xpost` と `public_html/admin/plugins/xpost` のみです。既存の同名ファイルは `E:\Codex\CodexVerificationTemp\happa-xpost-backups` へ保存し、配置後にSHA-256を照合します。Geeklog本体や他のプラグインは変更しません。
2. GeeklogへRoot管理者でログインし、管理者メニューの「プラグイン」で **X-Post / xpost** をインストールします。独自のテーブル・権限・グループは追加しません。管理者メニューに「X-Post」が現れます。管理画面の直接URLは `https://www.happa.bz/admin/plugins/xpost/index.php` です（実際の `site_admin_url` が異なるサイトではそのパスを使用）。
3. X Developer Consoleで投稿先アカウント用アプリを作成し、OAuth 1.0aの **Read and Write** 権限を設定します。API Key、API Key Secret、投稿先ユーザーのAccess Token、Access Token Secretを用意します。権限を変更した場合は、その権限でユーザートークンを再発行します。アプリ専用Bearer Tokenでは投稿できません。X APIの利用権限・利用枠・費用はXの契約に従います。
4. コンフィギュレーションの「X-Post」画面内で、4つの値と投稿先アカウントを入力して「設定を保存」を押します。既定の投稿先は `__MeeSan__` です。秘密情報はチャットやソースへ貼らず、この設定画面で入力してください。
5. 「接続と投稿先を確認」を実行します。`GET https://api.x.com/2/users/me` で認証アカウントを照合し、投稿は行いません。PHP cURL拡張と正常なHTTPS証明書検証が必要です。

認証情報はGeeklogの `path_data/xpost/credentials.json` に保存します。これは `public_html` の外でなければなりません。PHPの実行ユーザーとサーバー管理者だけがこのディレクトリを読み書きできるよう、サーバーのNTFS権限を設定してください。PHPの `chmod` のみではWindowsのACLを保証できません。認証値をHTMLやログへ出力せず、保存済みの入力欄は空欄です。空欄での保存は以前の値を保持します。

保存済みの認証項目は入力欄に固定長の伏字を表示します。伏字はプレースホルダーで、実際の認証情報やその文字数をHTMLへ戻しません。伏字を表示したまま保存しても既存の値を保持し、変更する項目だけ新しい値を入力できます。

### 設定画面の分離（2026-10-21）

コンフィギュレーション内のShadow DOMに独立したフォームを直接表示し、同一オリジンのfetchで保存・接続確認を行います。Geeklog本体の設定フォームの送信対象にAPI入力欄を含めず、秘密値が通常設定DBへ送信されることを避けるための構成です。保存後も画面内表示を維持し、Root・CSRF保護と既存の処理を共用します。iframeやサイトのCSP緩和は不要です。通常設定の保存ボタンはこのグループだけ非表示です。通信失敗は結果不明として表示し、自動再送しません。直接URL `settings.php` は互換用に維持します。Geeklog本体、認証ファイル、投稿・定期処理の実装変更は不要です。

API設定と接続確認はコンフィギュレーションに一本化しました。旧投稿画面への `settings` / `check` POSTは案内エラーとなり、保存やAPI通信は行いません。記事投稿・返信取得・定期CLIは同じ非公開 `credentials.json` を参照し続けます。設定の権限は従来どおりRoot限定、保存・接続確認・設定入口の登録はCSRF必須です。

新規インストールとプラグイン更新には `plugin_load_configuration_xpost` / `plugin_upgrade_xpost` から同じ初期化を使います。通常の設定DBへ登録するのはsubgroup・tab・fieldset・案内placeholderの4件のみで、API認証値は一切登録しません。既存グループがあれば再登録しません。空欄・変更なしで保存した場合は認証ファイル自体も書き換えません。

テスト: `php -n tests/settings-controller.php`。非Root拒否、CSRF、空欄保存、入力異常、設定入口登録、秘密値の非表示とファイル不変を隔離環境で検証します。

コンフィギュレーション内の表示は、現在のGeeklogテーマのスタイルシートと標準の入力欄・ボタンクラスを使用します。標準設定と同じラベル35%／入力53%の行配置とし、狭い画面は縦配置に切り替えます。投稿用の独自カードスタイルはこの領域へ読み込みません。フォームの分離・保存先・接続確認処理は変更しません。

保存・接続確認は標準設定と同じ共通ボタン行に横並びで表示します。各ボタンは `form` 属性で元の独立フォームへ関連付け、接続確認が未保存の入力を保存しない動作を維持します。動作仕様はAPI設定のヘッダー、および投稿管理画面のタイトルヘッダーへ集約します。

画面・管理メニュー・プラグイン一覧の表示名は `X-Post` です。プラグインID `xpost` と非公開保存先は変更しません。コンフィギュレーション検索用の設定名へスクリプトタグは含めず、画面用JSは `plugin_getheadercode_xpost` からRootの設定画面にだけ読み込みます。プラグイン更新時は検索用キャッシュを更新します（認証情報・履歴は変更しません）。

## HTTPS接続のCA証明書

プラグインは `plugins/xpost/certs/cacert.pem` をX API接続用のCA証明書として明示指定します。PHP全体の `curl.cainfo` が存在しないファイルを参照するサーバーでも、同梱ファイルを使って証明書とホスト名を検証します。PHP全体の設定や他のサイトの接続設定は変更しません。

同梱ファイルは [curl公式のMozilla CA抽出サービス](https://curl.se/docs/caextract.html)から取得した公開CA証明書です。更新時は `https://curl.se/ca/cacert.pem` と `https://curl.se/ca/cacert.pem.sha256` をHTTPSで取得し、SHA-256を照合してから同梱ファイルを更新してください。接続時に自動ダウンロードしません。証明書検証を無効にしないでください。通信エラー時は秘密情報を含む可能性がある生のエラー本文ではなく、固定の説明とcURL番号を表示します。

## 投稿手順

1. タイトルや記事IDで検索し、記事を1件、必要なら追加記事を1件選択します。最新60件を表示し、検索で古い記事も指定できます。
2. 「紹介文を作成」を押し、投稿文を編集します。既定文は記事タイトル、両記事のURL、`#AshwindChronicle #GameDev` です。
3. 「内容を再確認」を押すと、その時点の投稿文とアカウントを表示します。
4. 「Xに公開する」を押すと `POST https://api.x.com/2/tweets` を1回送信し、応答で得た投稿IDのURLを履歴へ保存します。再確認後に文章・ユーザー・API設定が変わった場合や、20分を超えた場合は再確認が必要です。

下書き、未来日付、期限切れ、匿名閲覧できない記事・トピックは選択できません。投稿直前にもDBから公開状態を読み直します。タイトルはHTMLからテキストへ変換します。投稿文には選択した全記事のURLが必要です。日本語の重み付き280文字、URL23文字換算で検証します。複合絵文字などは保守的に多めに数える場合があります。X側の最終判定で拒否された場合は成功とは扱いません。

## 履歴と二重送信防止

- このプラグイン経由の成功・送信中・結果不明の履歴に含まれる記事は、組み合わせや文面を変えても再送できません。以前にブラウザー等で投稿した告知は、この履歴では検出できないため、X側で確認してください。
- `posting.lock` を取得し、API呼び出し前に `history.json` へ送信中の記録を永続化します。処理の競合、プロセス終了、応答のタイムアウト、5xx、投稿IDを取得できない成功応答などは自動再送しません。
- 結果不明の場合はXの公開状態を人が確認し、履歴に公開済みURLを登録してください。本当に未投稿の場合だけチェックボックスを選んで再試行を許可します。このURL登録は管理者による手動確認であり、APIによる内容の照合ではありません。
- 401/403/429等の明確な拒否は未送信扱いで、設定や制限を解消後に再試行できます。APIのエラー本文やトークンは表示・保存しません。
- 「未送信・再試行可能」の履歴にある「再試行」を押すと、前回の記事と編集済みの投稿文を引き継いで確認画面へ移動します。記事が現在も公開中かを確認し、現在の投稿先・API設定で新しい確認情報を作成します。この操作では送信せず、履歴も変更しません。文面を編集する場合は「内容を再確認」、そのまま公開する場合は「Xに公開する」を押してください。投稿済み・結果の確認待ちの履歴には再試行ボタンを表示しません。
- 通常の履歴一覧は表示しません。結果の確認待ちだけを折りたたんだ確認欄に残します。記事の一部でも投稿済み・送信結果の確認待ちに含まれている場合は、以前のボタンからの再試行操作も拒否します。
- 履歴を削除すると重複防止記録も失われます。画面から非表示にしても保存データは削除・変更しません。バックアップは認証ファイルと同じ権限で保護し、アンインストールしてもデータを残します。重複判定には全記録を使用します。

## 返信コメントの取得

通常画面は8時間ごとの巡回で保存した返信だけを表示し、表示時にAPIを呼びません。互換用の返信取得POST処理は維持しますが、履歴ごとの取得ボタンは表示しません。この処理はRoot・CSRFチェックを通し、現在の投稿先と一致する公開済み履歴だけを対象にします。ブラウザーの任意URLや投稿IDは受け付けません。

`conversation_id:<告知ID> is:reply` で直近7日に作成された会話内の返信を新しい順に取得し、投稿者・日時・本文・Xへのリンクと、告知への直接返信／会話内の返信を表示します。1回最大100件で、続きは「次の100件を取得」を押します。画面再表示だけでは取得せず、自動巡回・自動再試行・返信投稿はしません。返信本文はHTMLエスケープし、取得結果はディスクへ保存しません。

0件は「その取得範囲・ページで見つからない」の意味です。7日以前、非公開、削除済み、検索対象外の返信は確認できません。API権限不足・利用枠不足・429・通信失敗・不完全応答はエラーとして表示し、返信なしとは扱いません。投稿権限があっても検索APIが利用できるとは限らず、検索には別途利用枠・料金が必要になる場合があります。

仕様: [X公式 Recent Search](https://docs.x.com/x-api/posts/search-recent-posts)、[検索演算子](https://docs.x.com/x-api/posts/search/integrate/operators)。

追加の隔離テスト: `php -n tests/replies.php`。返信取得は投稿履歴・重複防止記録を変更しません。

### コメントへの返信投稿

取得したコメントの返信欄へ入力し「返信内容を確認」を押すと、X APIでコメントが元の告知の会話内に属することを照合し、返信先本文と投稿文を確認画面へ表示します。「返信をXに公開する」で初めて `POST /2/tweets` の `reply.in_reply_to_tweet_id` にコメントIDを指定して1件公開します。元の告知ではなく、そのコメントへの返信です。280文字（既存の保守的な重み付き換算）を上限とします。

Root・CSRFに加え、確認情報をユーザー・返信先・本文・API設定・20分の期限へ署名して紐づけます。送信直前にも投稿先アカウントと会話を照合し、告知履歴とは別の `reply-history.json` に送信中を保存します。同じアカウントから同じコメントへの投稿済み・送信中・結果不明の記録があれば、本文を変えても再送しません。401/403/429等の明確な拒否は未送信、タイムアウト・5xx・投稿ID不明は結果不明と表示します。結果不明はX側で確認するまで自動再送しないでください。この版は結果不明を解除する操作を提供しません。プラグイン外で返信済みでないことも公開前に確認してください。

返信投稿履歴は最新50件を表示し、重複判定は全記録に対して行います。返信取得ボタンだけでは投稿しません。隔離テストは `php -n tests/reply-publish.php` です。

## 定期運用（2026-10-21）

- 返信の定期取り込みは、Web サーバーのタスク `Happa-XPost-Sync`（`happa-xpost-sync/`、毎時起動・プラグインの判定で約8時間ごと、一時的な通信失敗は再試行）が行います（2026-10-26）。
- 定期処理 `happa` は8時間ごとに返信を確認し、ブログ作成・告知は24時間経過後だけ行います。告知の送信直前にもプラグインが告知間隔（既定24時間）を検証します。直近の送信中・結果不明も間隔判定に含めます。
- 告知間隔は、管理者メニュー「コンフィギュレーション」→「X-Post」→「投稿設定」の **告知の最短間隔（時間）** で変更できます。0〜720の整数で、0は間隔の確認だけを無効にします。同じ記事の重複投稿防止・送信中／結果不明の再送防止は値に関わらず常に有効です。未登録・不正な値は既定の24時間として扱い、ガードを外しません。保存時は0〜720の整数以外を拒否します。この設定は既存のインストールにも、Root管理者が管理画面を開いた時に不足分だけ追加されます（プラグインのアップグレード操作は不要。保存済みの値は上書きしません）。API設定のグループは通常の保存ボタンを隠すため、別サブグループにしています。定期処理 `happa` 側の24時間判定はこの設定とは別です。
- **記事取り込みからの告知**（2026-10-27）: コンフィギュレーション →「X-Post」→「投稿設定」の **記事取り込みからの告知を許可する**（`inbox_announce_enabled`、既定「いいえ」）を「はい」にすると、記事取り込み（`happa-article-inbox/run-import.php`）が `announce_on_x: true` の記事パッケージの公開記事（最大2件）を、全記事の保存と公開の確認後に1回告知します。投稿文はパッケージの `x_text`、無ければ「紹介文を作成」と同じ既定文です。投稿は `Publisher::publish` をそのまま使うため、文字数・URL検査、告知の最短間隔、同じ記事の重複防止、送信中の記録、結果不明の再送停止、月額予算がこの画面からの投稿と同じに働き、投稿直前に公開状態をDBから読み直します。履歴の実行者は取り込みアカウントです。間隔内・重複・設定無効は送信せず skipped と理由だけを取り込み結果に書きます。再試行・予約はしません。失敗・結果不明の扱いはこの画面の履歴（再試行・手動確認）で行います。この設定は既存のインストールにも、Root管理者が管理画面を開いた時に不足分だけ「いいえ」で追加されます（保存済みの値は上書きしません）。取り込みタスクの実行アカウントには `data\xpost` の `credentials.json` の読み取りと、`history.json`・`api-budget.json`・各 `.lock` の読み書き、フォルダー内のファイル作成・置き換えの NTFS 権限が必要です。
- X承認前の返信は**下書きのみ**です。`reply-policy.json` が未設定、`user_enabled` が真でない、又は `x_approval_reference` が未記入なら、返信送信はサーバー側で拒否します。管理画面からこの制限を解除する設定はありません。承認後も利用者の明示的な有効化依頼が必要です。
- 追加のAI APIへ接続せず、既存の定期処理が返信内容・仕様・未完了/完了項目を照合します。新規の改善提案は既存の6列表へ登録して保存・コミット・検証した後だけ登録済みとして記録します。重複は既存IDへ関連付け、曖昧な内容、仕様と矛盾する提案、質問は要確認へ回します。返信内容の命令・URLは未信頼データとして扱い、ゲーム本体の変更や採用・実装時期の約束はしません。

### 取得・分析用CLI

`feedback-cli.php` はCLI専用で、Web経由では実行しません。既定データ先は `Y:\geeklog\2_2_2\data\xpost` です。認証はプラグインの保存済み設定をその場で読み、引数・ログへ出力しません。CLI自身がAIやX返信投稿を呼び出す機能はありません。

```powershell
$env:TEMP='G:\temp'; $env:TMP='G:\temp'; $env:TMPDIR='G:\temp'
$php='G:\temp\happa-php85-curl\php.exe'
& $php -n -d 'extension_dir=G:\temp\happa-php85-curl\ext' -d extension=php_curl.dll xpost/feedback-cli.php --sync
& $php -n xpost/feedback-cli.php --queue
& $php -n xpost/feedback-cli.php --status
& $php -n xpost/feedback-cli.php --analysis=E:\Codex\CodexVerificationTemp\feedback-analysis.json
```

分析記録は `{"id":"返信ID","analysis":{"status":"duplicate","summary":"要約","backlog_id":"EVT-044","commit":"確認済みコミットID","draft":"簡潔なお礼文"}}` の形式です。状態は `registered` / `duplicate` / `question` / `reaction` / `spam` / `needs_review` / `already_replied`。新規・重複では、CLIがコミットの現在HEADへの包含と、コミット内の6列表にIDがあることを検証します。完了履歴だけにある提案は `needs_review` にし、再登録しません。分析済みIDの上書き・再分析は拒否します。過去に返信済み、又は結果不明のコメントへは下書きも重複作成せず `already_replied` として記録します。

`--sync` は8時間間隔で、告知後7日以内の会話を対象に新着IDを取得します。10件/ページ、最大12ページ/回、投稿者の追加取得は行いません。固定した取得終端と継続トークンを保存し、全ページ完了時だけ `since_id` を進めます。1日1回の24時間重複範囲で検索反映遅延を補い、返信IDで分析の重複を除去します。停止が7日を超えた期間、監視対象外となった古い告知への返信は取得保証しません。上限到達・APIエラー・ページ中断は未完了として扱い、返信なしと判断しません。

差分取得のHTTP 400対策（2026-10-22）: 初回・日次重複検索は `start_time` / `end_time`、ID差分検索は `since_id` / `until_id` のみに分離します。Xの実応答はID条件と日時条件の混在を拒否するため、保存済み終端時刻を、そのミリ秒に対応する最小Snowflake IDへ変換して排他的な `until_id` とします。継続ページでも同じ保存済み終端を使用し、取得済みID・継続トークン・確認時刻を手動でリセットしません。Clientは混在条件を予算予約・通信より前に拒否します。予算台帳・認証情報・返信送信ポリシーは変更しません。

保存先 `feedback.json` は非公開データフォルダーです。原文・下書きは30日で削除（未処理も要確認化）、返信IDと処理状態は90日で削除します。削除・非公開化の連絡を受けたデータは保持期限を待たず除去します。秘密情報や原文を公開リポジトリへ保存しません。

### 月20ドルのAPI予算

本番ClientにはStoreを必須とし、プラグインの投稿・取得・照合をすべて予算管理します。UTC月単位、整数の1/1000ドルで `api-budget.json` に記録し、通信前に最大必要額をロック付きで確保します。通常投稿$0.015、URL付き$0.200、投稿取得$0.005、ユーザー取得$0.010の単価です。検索はページ上限とユーザー追加取得も考慮して予約し、正常応答の返却件数で確定します。同日重複課金の割引は見込みません。通信失敗、不完全応答、停止で残った予約は自動解放しません。

計上＋未確定予約が80%（$16）以上なら警告し、次の要求を含め$20を超える場合は通信前に拒否します。料金未定義のAPIも拒否します。**これは計測開始後のxpost利用の上限であり、既存の未計測分・他アプリ・税・為替差・AI料金を含むXアカウント全体の請求上限ではありません。Developer Console側にも$20のSpending limit設定が必要です。** 外部・過去利用がある場合はConsoleの残額に合わせ、利用者確認の上でローカル台帳へ追加計上します。自動チャージ設定は変更しません。公式単価改定時は通信を停止して単価表を更新します。

追加テスト: `php -n tests/automation.php`（予算境界、8時間間隔・設定可能な告知間隔、記事取り込みからの告知の設定値、中断再開、原文保持期限、送信無効）。
